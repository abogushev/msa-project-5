## Анализ проблем

1) Отсутствие пакетной обработки: Текущая система обрабатывает каждую запись из CSV-файла (до 1.2 млн в пик) в режиме, близком к онлайн, что создает нагрузку на СУБД.

2) Низкая производительность и масштабируемость: Монолитная архитектура не может просто масштабироваться под пиковую нагрузку. Все операции выполняются в одном процессе, что приводит к взаимным блокировкам и долгому ожиданию отклика системы для пользователей.

3) Отсутствие эффективного мониторинга и observability: Невозможно быстро диагностировать проблемы, узкие места или причины ошибок. Логи в файлах и метрики VM не дают общей картины.

4) Риск потери данных и ошибок: Пользователь должен ждать окончания обработки в браузере. При разрыве соединения или ошибке процесс может прерваться, и данные не будут обработаны, а пользователь не получит уведомления.

5) Сложность дальнейшего развития: Монолит затрудняет внедрение нового функционала.

## ADR
### Контекст
TradeWare необходимо обрабатывать большое количество CSV-отчетов о складских остатках, обеспечивая надежность, производительность и возможность масштабирования в преддверии роста нагрузки. Инжиниринг-лид имеет опыт работы со Spring Batch.

### Решение
Внедрить Spring Batch в качестве движка для пакетной обработки данных (ETL) в рамках существующего монолитного приложения. Вынести обработку из HTTP-запроса в асинхронный фоновый процесс.

### Обоснование

1) Стандарт де-факто для Java: Spring Batch предоставляет готовую, хорошо документированную инфраструктуру для пакетной обработки, что идеально подходит для данной задачи (чтение CSV -> преобразование -> запись в БД)

2) Производительность: Использование обработки порциями, например по 100-1000 записей снижает нагрузку на БД по сравнению с построчными операциями

3) Надежность: Встроенные механизмы retry, skip и повторного запуска после сбоя. Информация о выполнении заданий хранится в БД, что гарантирует отсутствие потерь данных при падении приложения.

4) Управляемость: Предоставляет готовые инструменты для мониторинга выполняемых заданий (через REST API или Spring Boot Actuator).

5) Низкий порог входа: Опыт лида в  Spring Batch ускорит внедрение

### Описание работы нового процесса
1) пользователь загружает CSV через веб-интерфейс на бекенд
2) бекенд сохраняет CSV в GCS
3) бекенд асинхронно запускает предопределенное Spring Batch Job, передавая ему путь к файлу в GCS
4) FlatFileItemReader читает CSV файл из GCS порциями
5) для каждой записи ItemProcessor обогащает данные, подтягивая актуальную информацию из справочников в БД
6) JdbcBatchItemWriter аккумулируют записи перед вставкой в БД
7) пользователь может в интерфейсе видеть статус обработки своего файла ("В обработке", "Завершено", "Ошибка"), который хранится в основной БД
8) по завершении Job может отправить событие уведомление пользователю о результате
